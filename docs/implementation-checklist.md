## Status definitions

- **Implemented**: exercised by a named deterministic check, within the stated scope.
- **Incomplete**: part of the requirement works but a demonstrated or inspected gap remains.
- **Unverified**: implementation exists but its required external/platform behavior has not been established.
- **Missing**: required mechanism or verification artifact is absent.

A requirement can have different statuses for deterministic behavior and live behavior. The two initial strict expected failures have been converted to ordinary passing regressions after the focused fixes. Passing these checks does not prove semantic truth. See [security review](security-review.md) for ranked findings and [evaluation](evaluation.md) for canonical commands and results.

## Harness assessment and acceptance gaps

Apply the harness ideas of repository-resident knowledge, mechanically enforced boundaries, actionable failure feedback, repeatable verification and human review. The reference is OpenAI's [Harness engineering](https://openai.com/index/harness-engineering/). Fetching that page returned HTTP 403 in this environment; the article was not freshly inspected and no claim of formal conformance or verbatim quotation is made.

- **Repository knowledge:** Keep `AGENTS.md` authoritative. Architecture explains boundaries; evaluation owns commands/results; this checklist owns requirement status; security review owns severity and remediation. Avoid copying instructions into another agent file.
- **Mechanical constraints:** Closed tool registry and strict inputs are stronger than prompt instructions. Offline tests now reject real Gemini construction, DNS/socket connections and sending UDP packets by default. Adversarial tests also prohibit subprocess/shell calls. These are testing guards, not an OS sandbox or a proof about every dependency.
- **Feedback:** Stage/category errors and assertions give localized failures without publishing model/log content. Strict expected failures expose known gaps; an unexpected pass fails the suite and triggers review. Never remove or loosen safety assertions to make the gate pass.
- **Repeatability:** One canonical local command sequence lives in evaluation docs. Pinned dependencies have no integrity hashes; vulnerability audits are separate network-dependent checks, not ordinary unit tests.
- **Missing harness controls (recommendations, not implemented):** automatic CI verification, a Windows/Python 3.11 test matrix, automated dependency/secret scanning and coverage measurement. These were not mandatory MVP features, but limit repeatability evidence. No framework or infrastructure was added for them.
- **Complexity to revisit, not refactor now:** generic dictionary-based diagnostic stage tracking; duplicated test-client helpers with different capture semantics; lengthy regex rules. Prefer focused typed/string helpers only after a reproducer justifies changes.

Acceptance for this audit: no new product features; instruction file identical; the initial audit changed only the High redaction issue; this authorized follow-up makes the focused Medium-severity corrections in the security review; adversarial tests use fictional inputs and no external requests; full suite has zero unexpected failures; each unverified external property remains visible; the original expected-failure assertions now pass normally. See security findings for proposed follow-ups requiring separate review.

## Medium-severity follow-up acceptance

- Consent: `test_app` checks unchanged reruns preserve approval while scenario/mode/file identity/file bytes/input errors and model changes clear it before execution.
- Resources: `test_resources` checks line/event/source/result/response/report bounds, a total API-call budget including reporting, shrinking per-request timeouts and rejection after the monotonic deadline. These are deterministic clock tests, not real network timing guarantees.
- Causal certainty: `test_reporting` and `test_agent` reject common explicit certainty claims across output fields and require unconfirmed status; the former adversarial expected-failure assertion passes. Novel wording and semantic support remain unverified.
- Sensitive data: `test_privacy` covers direct contexts, record metadata, known API-key echoes, escaped/multiline/cookie/JWT/PEM cases, line preservation, safe tool arguments and exports. Unknown encodings, memory retention and provider handling remain outside guarantees.
- Full suite after these fixes: **183 passed**, zero expected failures/skips. No live Gemini calls or Windows/browser verification were performed. `AGENTS.md` is unchanged; no commit/push is included in this follow-up.
